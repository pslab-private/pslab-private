기술 글을 어렵게 만드는 것은 문법보다 범위입니다. 충분히 설명하고 싶은 마음에 배경이 길어지고, 예제를 다듬다가 핵심 질문을 놓치기도 합니다. 글의 형식을 작게 정해두면 이런 부담을 줄일 수 있습니다.

## 제목에는 독자가 찾을 질문을 담기

“개발 일지”보다 “빈 배열을 처리할 때 발생하는 오류 해결하기”가 무엇을 얻을 수 있는지 잘 보여줍니다. 도구 이름과 증상, 해결하려는 문제 중 중요한 정보를 제목에 남겨보세요.

요약에는 글의 배경을 길게 설명하기보다 **어떤 문제를 어떤 방식으로 다루는지** 한두 문장으로 적습니다.

## 예제는 가장 작은 입력부터

실제 서비스 코드를 모두 옮기기보다 핵심 동작을 보여주는 예제를 고릅니다. 아래 코드는 값이 없을 때의 동작을 명확히 설명하기 위한 작은 예제입니다.

```ts file="average.ts"
function average(values: number[]): number | null {
  if (values.length === 0) return null;
  return values.reduce((sum, value) => sum + value, 0) / values.length;
}

console.assert(average([]) === null);
console.assert(average([2, 4, 6]) === 4);
```

코드 아래에는 무엇이 달라졌는지와 왜 그 동작을 선택했는지 설명합니다. 여기서는 입력이 없을 때 숫자를 만들어내는 대신 `null`로 표현하고, 호출하는 쪽에서 처리하도록 했습니다.

## 비교에는 표를 활용하기

서로 같은 기준으로 비교할 수 있는 내용은 표로 정리하면 찾기 쉽습니다.

| 구성 요소 | 남겨둘 내용                 |
| --------- | --------------------------- |
| 환경      | 도구와 버전, 재현 조건      |
| 입력      | 문제가 발생하는 최소 데이터 |
| 기대 결과 | 원래 의도한 동작            |
| 실제 결과 | 직접 관찰한 동작과 오류     |

넓은 표와 긴 코드는 모바일에서도 해당 영역 안에서 가로로 스크롤할 수 있습니다. 문장 전체를 코드 블록에 넣기보다 설명은 본문에 남기는 편이 읽기 좋습니다.

## 아직 확인하지 않은 내용은 구분하기

> [!NOTE]
> 실험 환경에서 확인한 결과와 모든 환경에서 성립하는 주장은 다릅니다. 적용 범위와 남은 질문을 함께 적어두세요.

추측과 측정 결과를 구분하면 독자가 자신의 환경에 적용할 때 무엇을 검증해야 하는지 알 수 있습니다.

## 마지막에는 다시 찾을 단서를 남기기

글과 관련된 태그를 2~4개 고르고, 참고한 공식 문서나 이전 글을 연결합니다. 내용이 달라졌을 때는 수정 날짜를 갱신합니다.

오늘 해결한 문제를 내일 다시 설명할 수 있다면 충분히 좋은 출발입니다.
