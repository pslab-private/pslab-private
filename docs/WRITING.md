# 글 작성 안내

## 가장 빠르게 시작하기

```sh
pnpm new-post debugging-a-timeout "타임아웃의 원인을 찾는 과정"
pnpm dev
```

한국어 `src/content/posts/debugging-a-timeout.md`와 영어 `src/content/posts/en/debugging-a-timeout.md` 초안이 함께 생성됩니다. 두 파일을 편집하고 http://localhost:4321/posts/debugging-a-timeout/ 와 http://localhost:4321/en/posts/debugging-a-timeout/ 에서 확인합니다. 초안은 개발 모드에서만 표시됩니다.

매번 할 일은 **제목·요약·본문 작성 → 대표 이미지 한 장 지정 → 미리보기 → `draft: false`로 바꾸고 `main`에 반영**입니다. 검증과 배포는 GitHub Actions가 자동으로 실행합니다.

홈의 전체 글 목록, 검색, RSS에는 자동으로 반영됩니다. 추천 여부나 노출 위치를 따로 정할 필요가 없습니다. 홈은 글 개수 제한 없이 모든 글을 발행일(수정일이 있으면 수정일) 기준 최신순으로 보여줍니다.

## 한국어·영어 함께 작성하기

새 글은 같은 파일명으로 한국어와 영어 마크다운을 함께 완성합니다. 영어본은 `src/content/posts/en/`에 두며 제목·요약·본문·표·캡션·대체 텍스트까지 번역합니다. 생성 명령은 영어 초안의 틀만 만들므로 에이전트가 글 내용에 맞는 영어 제목과 본문을 직접 작성해야 합니다. 영어 제목을 미리 지정하려면 세 번째 인수를 사용할 수 있습니다.

```sh
pnpm new-post debugging-a-timeout "타임아웃의 원인을 찾는 과정" "Tracing a Timeout"
```

두 파일의 `pubDatetime`, `modDatetime`, `tags`, `coverImage`, `draft`를 맞춥니다. 태그는 같은 식별자를 사용하며 영어 표시명만 `src/i18n/locale.ts`에서 관리합니다. 수치·단위·수식·공개 코드·출처와 실험의 한계도 일치해야 합니다. 본문 내 다른 글 링크는 영어본에서 `/en/posts/.../`로 연결하고 미디어는 같은 `/media/...` 파일을 재사용합니다. `src/assets/` 이미지를 상대 경로로 참조하면 영어 파일의 폴더 깊이가 한 단계 더 깊다는 점에 주의합니다.

글 수정 시 두 버전을 함께 갱신하고 완성한 뒤 둘 다 `draft: false`로 바꿉니다. 한국어·영어 글은 각각의 목록·검색·RSS(`/rss.xml`, `/en/rss.xml`)에 표시됩니다.

홈(`/`)에서는 저장된 언어 선택을 우선 사용하고, 없으면 브라우저 선호 언어 중 한국어·영어를 순서대로 확인합니다. 지원하는 언어가 없으면 영어를 표시합니다. 상단의 **한국어 / English**로 바꾸면 선택을 기억합니다. 개별 글이나 영어 주소를 직접 열면 해당 주소의 언어가 유지됩니다. 자바스크립트나 브라우저 저장소를 사용할 수 없어도 언어 링크는 작동합니다.

## 글의 기본 정보

```yaml
---
title: "타임아웃의 원인을 찾는 과정"
description: "어떤 환경에서 발생한 문제를 어떻게 해결했는지 소개합니다."
coverImage: "/media/debugging-a-timeout/result.png"
pubDatetime: 2026-11-09T10:00:00+09:00
draft: true
---
```

| 필드          | 작성 규칙                                                                    |
| ------------- | ---------------------------------------------------------------------------- |
| `title`       | 제목. 따옴표로 감싸면 콜론 등을 안전하게 입력할 수 있습니다.                 |
| `description` | 글 목록·검색·공유용 요약. 필수 항목입니다.                                   |
| `coverImage`  | 작성자가 직접 고른 핵심 이미지 한 장. 이미지가 없는 글만 빈 문자열로 둡니다. |
| `pubDatetime` | 글 생성 시 자동 입력됩니다. 며칠 뒤 발행하면 실제 발행일로 맞춥니다.         |
| `draft`       | `true`면 배포 결과, 검색, RSS에서 제외합니다. 발행 시 `false`로 바꿉니다.    |

나머지는 필요할 때만 추가합니다.

| 선택 필드     | 용도                                                                         |
| ------------- | ---------------------------------------------------------------------------- |
| `tags`        | 주제별로 찾게 하려면 추가합니다. 예: `["네트워크", "문제 해결"]`. 생략 가능. |
| `modDatetime` | 수정일을 별도로 표시하고 목록 위로 올리고 싶을 때 추가합니다.                |
| `author`      | 선택 항목. 생략하면 사이트의 기본 작성자를 사용합니다.                       |
| `hideToc`     | `true`면 해당 글의 목차를 숨깁니다.                                          |

**공개 저장소의 초안 원문도 공개됩니다.** `draft`는 사이트 표시 여부만 제어합니다.

미래 날짜의 글은 해당 날짜 이전의 배포 빌드에서 제외됩니다. 날짜만 설정한다고 자동 발행되지 않습니다. 발행일에 수동으로 빌드를 실행하거나 `main`에 변경을 반영하세요. 기본 워크플로에는 예약 실행을 넣지 않았습니다.

## 본문 작성

제목은 자동으로 표시되므로 본문은 `##`부터 시작합니다. `##`, `###` 제목은 자동으로 목차에 표시됩니다.

````markdown
## 문제 상황

문단 사이에는 빈 줄을 둡니다. **강조할 내용**과 `짧은 코드`를 쓸 수 있습니다.

### 재현 코드

```ts file="example.ts"
const message = "안녕하세요";
console.log(message);
```

> [!NOTE]
> 본문 흐름에서 분리할 보충 설명입니다.

- 첫 번째 항목
- 두 번째 항목

| 방법    | 결과        |
| ------- | ----------- |
| 변경 전 | 관찰한 결과 |
| 변경 후 | 검증한 결과 |
````

일반적인 글은 `.md`를 쓰면 충분합니다. 컴포넌트를 직접 넣어야 하는 글에서만 `.mdx`를 사용하세요. Mermaid와 수식 렌더링은 별도 설정이 필요하며 현재 기본 구성에는 포함하지 않았습니다.

## 코드와 첨부 자료의 공개 기준

회사·프로젝트의 프로덕션 코드와 비공개 로컬 라이브러리는 글에 싣지 않습니다. 문서용 로컬 라이브러리나 예제 ZIP에도 포함하지 않습니다. `public/`에 넣은 파일은 본문에서 링크하지 않아도 배포되므로 압축 파일 내부까지 확인합니다.

의사코드와 예제는 공개 라이브러리·표준 라이브러리의 공개 API만 사용해 새로 작성하고 공식 문서나 공개 저장소의 버전·출처를 연결합니다. 로컬 모듈 import, 비공개 래퍼와 프로젝트 전용 함수·커널은 사용하지 않습니다. 공개 라이브러리의 `_src` 등 내부 구현 경로에도 의존하지 않습니다.

실행해 검증하지 않은 예제는 의사코드라고 표시하고 입력과 생략한 조건을 설명합니다. 구현을 공개할 수 없는 부분은 원리·수식·처리 순서로 풀어 씁니다. 실험 측정값은 새로운 근거 없이 바꾸지 않습니다. 에이전트의 전체 준수 기준은 [AGENTS.md](../AGENTS.md)에 있습니다.

## 이미지 추가

### 대표 이미지 지정

이미지가 있는 글은 작성자가 핵심 이미지 한 장을 골라 `coverImage`에 지정합니다. 본문의 첫 이미지나 공유 이미지를 자동으로 가져오지 않습니다. 본문에 이미 있는 이미지나 영상의 포스터를 재사용할 수 있어 별도의 썸네일을 만들 필요는 없습니다.

```yaml
coverImage: "/media/my-note/result.png"
```

위 예시는 `public/media/my-note/result.png`를 사용합니다. 대표 이미지는 `public/` 아래에 넣고 `/media/...`처럼 사이트 기준 경로로 지정합니다.

홈·전체 글·태그·아카이브 목록에서 이 이미지와 제목·요약을 함께 보여줍니다. 기술 도표나 비교 장면이 잘리지 않도록 이미지 전체를 표시합니다. 이미지가 없는 글은 `coverImage: ""`로 두거나 항목을 생략하면 빈 이미지 영역 없이 글만 표시됩니다. 글별 공유 이미지는 제목·요약으로 별도 자동 생성됩니다.

### 본문 이미지

글에 사용할 이미지를 `src/assets/images/글-주소/` 아래에 넣는 것을 권합니다. 이 위치의 이미지는 Astro가 최적화합니다.

```markdown
![실행 결과를 비교한 화면](../../assets/images/my-first-note/result.png)
```

위 경로는 `src/content/posts/my-first-note.md` 기준입니다. 하위 폴더에 글을 넣으면 상대 경로도 함께 조정하세요. 이미지 설명에는 무엇을 보여주는지 적습니다.

`public/`의 이미지는 최적화 없이 그대로 배포됩니다. 예를 들어 `public/images/result.png`는 본문에서 `/images/result.png`로 연결합니다. 이 사이트는 도메인 루트(`/`)에 배포되므로 이미지와 글 주소에 저장소 이름을 붙이지 않습니다. 공유용 이미지는 각 언어의 제목과 요약으로 자동 생성됩니다. 목록의 대표 이미지는 작성자가 본문 이미지 등에서 한 장을 직접 지정합니다.

## VS Code에서 버튼과 입력란으로 관리하기

1. 권장 확장 프로그램 **Front Matter CMS**를 설치합니다.
2. 이 저장소 폴더를 열고 Front Matter 대시보드를 엽니다.
3. 저장소에 포함된 `frontmatter.json`을 그대로 사용합니다. 재초기화할 필요는 없습니다.
4. 글 목록과 제목·요약·초안 항목을 편집하고 대표 이미지 한 장을 선택합니다. 태그는 선택 사항입니다.
5. 터미널에서 `pnpm dev`를 실행한 상태로 미리 봅니다.

새 파일 생성은 위의 `pnpm new-post` 명령을 권합니다. 편집기에서 저장만 하면 로컬에 반영되며, 웹에 게시하려면 `draft: false`로 바꾸고 Git 커밋과 push를 합니다.

## GitHub에서 간단히 수정하기

저장소의 Markdown 파일을 열고 연필 버튼으로 수정하거나, 저장소 화면에서 `.`을 눌러 github.dev 편집기를 엽니다. 커밋을 `main`에 반영하면 자동 배포됩니다. 웹 편집기의 Markdown 미리보기는 블로그 디자인 전체를 재현하지 않으므로 큰 변경은 로컬에서 확인하세요.

## 글의 주소 관리

파일명은 글 주소가 됩니다. 발행한 글의 파일명이나 폴더를 바꾸면 기존 링크도 바뀌므로 가능한 유지하세요.

```text
src/content/posts/my-note.md           → /posts/my-note/
src/content/posts/web/my-note.md       → /posts/web/my-note/
src/content/posts/_2026/my-note.md     → /posts/my-note/
```

같은 최종 주소를 가진 파일을 두 개 만들지 않도록 주의하세요. 관리 편의를 위해 처음에는 글을 `src/content/posts/`에 평평하게 두고 태그로 분류하는 것을 권합니다.

## 발행 전 확인

- 제목·요약·본문과 직접 지정한 대표 이미지를 확인합니다. 이미지가 없는 글은 대표 이미지를 비워둡니다. 오래 작성한 초안이면 발행 날짜도 맞춥니다.
- 코드, 이미지, 표를 모바일 화면에서도 확인합니다.
- 개인정보와 내부 주소, 비밀 키가 없는지 살펴봅니다.
- 프로덕션 코드·비공개 로컬 모듈이 본문이나 첨부 자료에 없는지 확인하고, 코드·의사코드의 라이브러리 공개 출처를 연결합니다.
- `draft: false`로 바꾸고 GitHub의 `main`에 반영합니다. 검증과 배포가 자동 실행됩니다.
- Actions의 배포 성공 여부를 확인합니다. 로컬에서도 검증하려면 `pnpm test`, `pnpm build`, `pnpm verify`를 실행할 수 있습니다.
